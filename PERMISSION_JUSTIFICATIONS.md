# Audioura — Permission Justification Copy

Ready-to-paste text for store forms and platform permission prompts. Covers **microphone** and
**location** — the two sensitive permissions Audioura uses. Keep these consistent with the privacy policy
and the Data Safety / Privacy Nutrition forms, or review will flag a mismatch.

---

## iOS — Info.plist usage description strings

These appear verbatim in the system permission dialog. Add to `Info.plist`:

```xml
<key>NSMicrophoneUsageDescription</key>
<string>Audioura uses the microphone so you can speak a destination or request and have a tour generated by voice. Audio is used only to fulfill your request.</string>

<key>NSLocationWhenInUseUsageDescription</key>
<string>Audioura uses your location to create audio tours for places near you and to show tour stops on the map. Location is used only while you are using the app.</string>
```

If the app ever requests background location (it should NOT for v1 unless tours play hands-free while walking):

```xml
<key>NSLocationAlwaysAndWhenInUseUsageDescription</key>
<string>Audioura uses your location while you walk a tour so audio and map stops stay in sync with where you are.</string>
```
> v1 recommendation: request **When-In-Use only**. Background/Always location triggers extra App Store scrutiny and a stronger justification burden. Avoid unless a feature truly needs it.

## Android — runtime permission rationale (shown before the system prompt)

**Microphone (`RECORD_AUDIO`):**
> "Audioura needs microphone access so you can speak your destination or request instead of typing. We only listen while you're actively giving a voice command."

**Location (`ACCESS_FINE_LOCATION` / `ACCESS_COARSE_LOCATION`):**
> "Audioura needs your location to build tours for places around you and to pin tour stops on the map. We only use location while the app is open."

> Do **not** declare `ACCESS_BACKGROUND_LOCATION` for v1 — it requires a separate Play review and a video demo justifying background use.

## Google Play — Data Safety form answers

| Question | Answer |
|---|---|
| Does the app collect or share user data? | Yes |
| **Location (Approximate/Precise)** — collected? | Yes |
| — Purpose | App functionality (generate nearby tours, map pins) + Personalization (relevant local offers in Treats). Note: because Treats shows offers, also tick "Advertising or marketing" if Play flags it — but data is NOT shared with ad networks. |
| — Shared with third parties? | Yes, with service providers for app functionality only (not sold) |
| — Processed ephemerally / optional? | Optional; collected only when user requests a location-based tour |
| **Microphone audio** — collected? | Yes |
| — Purpose | App functionality (voice input to request a tour) |
| — Stored or ephemeral? | Processed to fulfill request; not used for advertising |
| **Device identifier** — collected? | Yes — App functionality (no email/password account; users are identified by device) |
| **Other info — third-party news subscription credentials (username & password)** | Yes, **only if the user connects a paid news subscription** — App functionality (log in to retrieve requested article text). Encrypted in transit. NOT shared, NOT used for ads. |
| **App activity / generated content** | Yes — App functionality (save & re-download tours) |
| **Crash logs / diagnostics** | Yes — Analytics / app performance |
| Is data encrypted in transit? | Yes (HTTPS) |
| Can users request data deletion? | Yes — in-app account deletion + email request |

**Permission declaration text (Play listing "why this app needs permissions"):**
> "Microphone: optional voice input to request tours. Location: to generate nearby tours and place map stops. Both are used only while the app is in use. Audioura does not sell personal data."

## iOS — Privacy Nutrition labels (App Store Connect → App Privacy)

Declare the following "Data Used to Track You": **None.**
Declare "Data Linked to You":
- **Location (Precise)** → App Functionality
- **Audio Data** → App Functionality
- **Device ID** → App Functionality (no email/password account)
- **Sensitive Info / Other Data (third-party subscription credentials)** → App Functionality, only if user connects a subscription
- **User Content (generated tours)** → App Functionality
- **Diagnostics (Crash Data)** → App Functionality / Analytics

> Keep this list identical in meaning to the Android Data Safety answers and the privacy policy table.
> Mismatches between these three are the most common privacy-related rejection reason.
