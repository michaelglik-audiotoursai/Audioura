## BLOCKER — search / download / play sub-steps of the live smoke test
The remaining live sub-steps (type "Venice, FL" into search → place the map → download one
EXISTING tour → play 5 s, with screenshots) require driving the app UI on the simulator. This is
blocked, and I document it rather than fabricate a pass:

1. **Host synthetic input to the Simulator is blocked by macOS TCC.** This terminal lacks the
   Accessibility (and Screen-Recording) grant, which cannot be granted from within the session.
   - `cliclick` **cursor movement works** (`cliclick m:` then `cliclick p` reports the new
     position), but **click events never register** in the simulator. Verified across four
     attempts on three distinct, well-separated targets ("Got it" button, the search icon, and
     the large "List" button): each screenshot after the click was unchanged.
   - `screencapture` of the host display fails ("could not create image from display").
   - `osascript`/System Events reports **0 windows** for the Simulator process and cannot
     enumerate or click its device view. `keystroke`/`cliclick` calls return exit 0, but exit 0
     is not delivery confirmation — the events are silently dropped by TCC.

2. **The permission-free alternative was assessed and judged out of scope for this task.** The
   repo's sanctioned way to drive the app on the simulator is `flutter drive` with an
   `integration_test` target (in-VM taps, no host Accessibility). A new end-to-end driver could
   dismiss the notice, search, download and play. However:
   - A subscribed build resolves to the **production** cloud stack
     (`https://subscribed-api.audioura.com`, `Endpoints.baseForTrack('subscribed')`), so the
     download step would hit the live production backend. Under the `$0.05` budget and the
     "never write the live DB / download an EXISTING tour only" constraints, I did not want to
     drive an automated, un-pinned download against production.
   - The HomeScreen (5000+ lines) builds tour rows and the download/pay/language dialogs
     dynamically from live network results with no stable widget `Key`s, so a reliable automated
     finder for "the right existing tour row → download → player → play 5 s" is fragile.

   Writing such a test is the correct next step if the live download/play evidence is required; it
   needs either Accessibility granted to the terminal (so the simple host-driven path works) or a
   decision to drive a pinned existing tour through `flutter drive` against production within
   budget.
